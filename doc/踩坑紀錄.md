以下是這次在 macOS 輸入法開發、安裝、註冊、顯示名稱與系統列表上踩到的坑，整理成之後可直接照做的注意事項。

**1. 先分清楚三件事**

- `LaunchServices` 看得到 app，不代表系統輸入來源清單一定會顯示。
- `TISRegisterInputSource` 成功，不代表輸入法已經可選取。
- `TISEnableInputSource` 回 `0`，也不代表系統一定已把狀態落地到 `.HIToolbox`。

**2. HIToolbox 真正重要的鍵**

- `~/Library/Preferences/com.apple.HIToolbox.plist` 裡，真正要看的不是只有 `AppleEnabledInputSources`。
- 實際更重要的是：
  - `AppleInputSourceHistory`
  - `AppleSelectedInputSources`
- 很多時候系統 UI 顯示與目前選取狀態，是靠這兩個鍵，不是單靠 `AppleEnabledInputSources`。

**3. 安裝流程正確順序**

- 正確順序是：
  1. `TISRegisterInputSource`
  2. 重新用條件搜尋拿回新的 `TISInputSourceRef`
  3. 先處理 parent source
  4. 再處理 mode source
- 不要拿舊的 `TISInputSourceRef` 繼續做 enable/select 判斷。

**4. 先看 parent，再看 mode**

- 一開始不要糾結 mode 名稱。
- 先確認 parent source：
  - 找得到
  - `enableCapable = true`
  - `TISEnableInputSource(parent)` 有沒有真正落地
- 再去看 mode source：
  - source id 是否正確
  - 是否 `enableCapable = true`
  - 是否 `selectCapable = true`

**5. select 不要硬用 API 當唯一標準**

- `TISSelectInputSource(mode)` 很容易回 `-50`。
- 這不一定代表整個輸入法無法被系統接受。
- 第一次真正加入輸入法，很多時候還是要透過系統 UI 手動選取。
- 實測上，`select` 不是最可靠的成功標準；是否出現在系統新增輸入來源清單，反而更重要。

**6. mode ID 一定要唯一，不能撞**

- 舊 mode ID 殘留不是小問題。
- 如果 controller / language model 邏輯還把目前輸入源當成別的 bundle 的 mode，enable/select 會出問題。
- mode ID 不能用過度裸的值，例如只寫 `Bopomofo`。
- 要用唯一值，例如：
  - `com.vader.inputmethod.FastChIME.Bopomofo`

**7. 不要直接 clone 已安裝的 IME 來改**

- 這是這次很大的坑。
- 直接複製已安裝、已在系統裡註冊過的 `McBopomofo.app`，再改名字或局部內容，會污染 mode 註冊結果。
- 實測會出現：
  - mode ID 被系統讀成雙重前綴
  - 例如 `org.openvanilla.inputmethod.McBopomofo.McBopomofo.Bopomofo`
- 所以不要用「複製已安裝 IME 再改」當正式路線。
- 正確做法是：
  - 從 source build 出唯一新 app
  - 系統裡同時只掛一份要測的版本

**8. bundle id / source id 形狀要保守**

- `bundle identifier` 最好包含 `inputmethod`。
- 目前可用正式版用的是：
  - `com.vader.inputmethod.FastChIME`
- `TISInputSourceID` 也對齊同一條 parent id。
- mode ID 再接：
  - `.Bopomofo`

**9. InputMethodConnectionName 要完全一致**

- `Info.plist` 的 `InputMethodConnectionName`
- 與程式碼中 `IMKServer(name: ...)`
- 這兩個值必須完全一致。
- 建議格式：
  - `$(PRODUCT_BUNDLE_IDENTIFIER)_Connection`

**10. controller / delegate class 名稱**

- 對 Swift 最小骨架來說，class name 形狀會影響 IMK 是否正常載入。
- 但這次實測也證明：它不是唯一根因。
- 不過仍建議固定使用一套已驗證過的可用形狀，不要來回變動。

**11. mode plist 形狀真的會影響能不能過 TIS**

- mode dict 少欄位時，常見症狀是：
  - 找得到 source
  - 但 `enabled=false`
  - 或 `select=-50`
- 把 mode 定義往已知可用版靠近後，至少可以把 `enabled` 做到 `true`。
- 所以不要只改名稱；mode dict 的欄位形狀要穩定。

**12. 顯示名稱是另一層問題**

- parent 顯示名稱與 mode 顯示名稱不是同一個來源。
- `CFBundleName` / `CFBundleDisplayName`
  - 影響 app / parent 顯示名稱
- `InfoPlist.strings` 裡對應 mode ID 的鍵
  - 影響 mode 顯示名稱
- 系統授權視窗顯示的字樣，未必即時吃目前 app 內的字串，可能受快取影響。

**13. 系統清單快取很重**

- `TextInputMenuAgent`
- `cfprefsd`
- `LaunchServices`
- `.HIToolbox`
- 這幾層都會殘留舊狀態。
- 很多時候就算 app 已改對、也重新註冊，系統 UI 還是不更新。
- 這台機器上實測最有效的最後手段是：
  - 登出再登入

**14. ASCII 外層檔名對 notarization / 打包比較穩**

- 實際安裝到 `~/Library/Input Methods` 的 app 可以是中文名。
- 但送 notarization 的 stage / zip，外層用 ASCII 名稱比較穩。
- 這次正式流程使用：
  - stage: `FastChIME.app`
  - zip: `FastChIME-YYYYMMDD-HHMMSS.zip`

**15. notarize 對進系統清單很重要**

- 本機開發版只做 `Developer ID` 簽章，不一定會穩定進輸入來源清單。
- 這台機器上，真正穩定出現在系統清單的是：
  - `Developer ID`
  - notarization `Accepted`
  - `staple` 完成
- 所以要分兩條流程：
  - 開發快迭代：不 notarize
  - 驗證系統列表 / 正式安裝：要 notarize

**16. dev / release 流程要分開**

- 已建立兩個捷徑：
  - `build-dev.command`
  - `build-release-notarize.command`
- 日常功能開發先走 dev。
- 只有在要驗證「系統是否真的辨識進清單」時，才走 notarize。

**17. 不要隨便移掉原本可用的輸入法**

- 原始 `McBopomofo.app` 可能是你日常正在用的。
- 測試新輸入法時，可以暫時移開測試版或舊 clone。
- 但不要把真正的原始輸入法當成一般測試垃圾一起刪或一起移除。

**18. 目前已驗證可用的正式基線**

- 專案目錄：
  - `fastChIME`
- 正式 app：
  - `快捷中文輸入.app`
- bundle id：
  - `com.vader.inputmethod.FastChIME`
- parent source id：
  - `com.vader.inputmethod.FastChIME`
- mode id：
  - `com.vader.inputmethod.FastChIME.Bopomofo`

**19. 建議之後不要再亂動的識別欄位**

- `CFBundleIdentifier`
- `TISInputSourceID`
- mode ID
- `InputMethodConnectionName`
- app 名稱
- 安裝路徑名稱

之後如果只是改輸入法功能，例如：
- 按鍵處理
- 組字邏輯
- 候選字
- 顯示行為

就不要再改上面這些 identity 欄位，否則每次都會重新踩系統快取與註冊問題。

**20. IME 內自開候選視窗，sandbox 會直接害你看不到**

- 這次最關鍵的新坑是：
  - 在 `fastChIME` 內，只要 entitlements 開了 `com.apple.security.app-sandbox`
  - `handle(_:)` 明明有跑到
  - `updateCandidateWindow(...)` 也有跑到
  - 但 IME 內自己開的候選窗 / probe window 就是完全看不到
- 同一份程式碼下，拿掉 `app-sandbox` 後：
  - 候選視窗立刻能出現
  - `兼具` 之類的詞也能正常顯示候選
- 所以如果你要驗證：
  - IME 內自開 `NSWindow` / `NSPanel`
  - 候選選單
  - probe 視窗
  先檢查 entitlements，不要只懷疑 plist、build、或候選資料。
- 目前實測對照：
  - 原始 `~/Library/Input Methods/McBopomofo.app` 的 entitlements 是空的
  - 我們開發版一開始有 `app-sandbox`
  - 候選窗就是因此一直不出來
- 結論：
  - 如果要在 IME 內自己管理候選窗，先以「不開 app sandbox」作為可用基線
  - 等功能穩了，再評估是否真的需要把 sandbox 加回來，以及加回來後要換哪種 UI 路線

**21. `setMarkedText` 不能拿來硬塞候選清單**

- `setMarkedText` 只適合顯示真正的組字內容。
- 這次實測把 debug 與候選一起塞進 `setMarkedText` 後，host app 會出現：
  - 組字內容被污染
  - 候選與 debug 文字混在一起
  - 明明候選邏輯正常，畫面卻像選錯字
- 所以之後：
  - `setMarkedText` 只顯示 composing text
  - 候選 UI 走 helper 視窗或之後真正可行的候選窗

**22. 真正可見的候選 UI，目前是外部 helper，不是 IME 內 candidate window**

- 目前穩定可見的是外部 helper 視窗。
- 它是透過：
  - `DistributedNotificationCenter`
  - `imeStateNotification`
  來接 IME 狀態。

**23. Host app / probe / 正式 IME 的游標策略必須完全一致**

- 這次最後定下來的方向，不是雙游標，而是更接近 vChewing / 小麥注音的單一真游標模型。
- 規則是：
  - `HostSelfTestEngine`
  - `IMEProbeSupport`
  - 正式 `SessionCtl`
  三邊都只能有一個真正可寫入的 token cursor。
- 真游標負責：
  - 真正的組字焦點
  - 新注音插入到哪個 token 位置
  - `Backspace` / `Delete` 應該刪哪裡
  - 候選 focus 應該看哪一段
- 顯示上的 caret 位置，不應再是另一份長期 state。
- 正確做法是：
  - display cursor 由真游標推導
  - candidate cursor 也由真游標推導
  - 不要再維持 `internal cursor` / `visible cursor` 兩套都能漂移的來源
- 只要之後改：
  - 左右移動
  - 中途插入
  - `Backspace`
  - `Delete`
  - focus segment
  - marked text caret 顯示
  都必須先在 host / probe 定義清楚，再同步搬到正式 IME。
- 不接受「host app 先能用，正式版之後再補齊」。
- 正確順序應該是：
  1. 先在 `HostSelfTestEngine` 定義行為
  2. 用 `IMEProbeSupport` 做 raw / reading probe 驗證
  3. 再把同一套狀態模型搬到正式 IME
  4. 驗證三邊在同一情境下輸出一致
- 一開始 helper 視窗如果在切換輸入法時就跳出，通常不是候選邏輯壞掉，而是：
  - `activateServer()` 發了非空狀態
- 正確做法：
  - activate/deactivate 時只發空狀態
  - 只有真的有 composing / candidates 時才顯示 helper

**24. 未完成讀音不能直接參與正式組詞**
- 這次 mixed merge 另外踩到三個實際坑：
- `天氣verygood` 之所以一開始一直失敗，不是單純英文詞庫沒命中，而是中文 fixed span 對齊錯了。
- 真正問題是：
  - `buildFixedPrimaryCoverages(...)` 如果直接信任 `segment.rawLength`
  - 中文 phrase segment 可能只會拿到 `length`，不是實際 raw key 長度
  - 例如 `天氣` 會被錯當成 `0..2`，不是 `wu0fu4` 的 `0..6`
- 正解是：
  - 對中文 fixed span 現場用 `keySequence(for:[reading])` 重算 raw 長度

- 第二個坑是英文 provisional span 的早停條件。
- 如果掃到 `veryg` 這種中間點就因為 `!exact && !canExtend` 直接停掉，
  後面的 `verygood` 永遠不會被看到。
- pure latin span 不應在這裡提早 `break`。

- 第三個坑是 provisional 英文分數不能亂拉高。
- 太低：會退回垃圾注音 fallback
- 太高：會把 `verygood` 整段吃掉，贏過 `very good`
- 正確策略是：
  - provisional 英文高於垃圾注音
  - exact 英文分詞高於 provisional 整段
  - 這樣 `天氣verygood` 才會穩定收成 `天氣 very good`

- 這次反覆踩到的：
  - `一˙ㄒ` 變成 `一醫師`
  - `很正常了 + ˙` 吐出怪字或聲調
  - `Backspace` 後一個單子音被誤判成別的字
- 根因都一樣：
  - 把 `currentReading` 這種未完成讀音，過早拿去做正式 segment resolve / candidate 判斷
- 之後固定規則：
  - `readings` 只放已完成音節
  - `currentReading` 只當未完成音節 buffer
  - 候選與組詞優先看 `readings`
  - `currentReading` 最多只做顯示，不應跨詞參與正式決策
- 只有在音節完成時，`currentReading` 才能進 `readings`。
- 小麥注音 / vChewing 共同的保守策略，就是把未完成讀音和正式組詞材料分開。

**25. 方向鍵很容易被誤判成 raw commit / numericPad / function glyph**

- 這是實際踩過的坑。
- `↑ / ↓` 明明想做選字，最後卻可能走到：
  - `commitRawText`
  - `numericPad`
  - `shiftedPassthrough`
- 不能只靠單一 `keyCode` 判斷。
- 要做的是：
  - 先把最近幾個事件放進 queue
  - raw commit 前再看 queue
  - 若近幾個事件含方向鍵 / function arrow，就直接 suppress raw commit
- 這一層是目前讓 `兼具` 等詞在 `↑ / ↓` 時不再直接送出的關鍵。

**26. 自測不能只做整句 round-trip，一定要逐鍵模擬**

- 之前有一度看起來「全通過」，但那是因為只測：
  - 整段 reading -> 最後輸出
- 這種測法太樂觀。
- 一改成逐鍵輸入模擬後，短句問題會立刻暴露：
  - 音節切分
  - 無聲調連打
  - 高頻同音誤選
- 所以之後回歸測一定要包含：
  - 短詞逐鍵
  - 短句逐鍵
  - 短文逐鍵或分段逐鍵

**27. 真實例子比 synthetic selftest 更重要**

- selftest 只能當 smoke test。
- 真正高價值的是使用者直接打出來的真實句子，例如：
  - `我先測試一下`
  - `還是多測試吧`
  - `目前看起來蠻正常的`
- 這些例子會揭露：
  - phrase 優先失敗
  - 姓氏或冷字搶首選
  - focused segment 候選策略不穩
- 所以修正優先順序應該是：
  1. 真實例子
  2. 逐鍵 selftest
  3. 再來才是漂亮的排序或 UI

**28. 音節完成規則要固定，host / debug / IME 必須一致**

- 這條和單一 truth source 是同一件事。
- 只要：
  - live IME
  - `IMEProbeSupport`
  - CLI / host selftest
  三邊對 `focus`、`candidate`、`commit` 的資料來源不一致，就會再次出現：
  - PREVIEW 正常、commit 錯
  - 候選選到英文，但套回中文 span
  - 單字候選 index 對錯 span

**29. mixed 候選不能只傳字串**

- 這次實際踩到的根因之一，是候選窗與選字流程中途把 mixed 候選降成純 `String`。
- 一旦候選只剩字串，就會失去：
  - 它是哪個語言
  - 它要替換哪個 span
  - 它是 primary 還是 secondary
- 最後就會出現：
  - `選了 up，卻變成 因`
  - PREVIEW 和 commit 對不上
- 現在固定原則：
  - mixed 候選正式資料必須保留 metadata
  - 至少包含：
    - `text`
    - `languageID`
    - `replacementKey`
  - UI 顯示時才把它轉成字串

**30. 候選移動不能只有單邊循環**

- 這次又踩到：
  - `↑` 可以尾接頭
  - `↓` 卻不行
- 這種狀況很容易讓使用者誤判成選單壞掉，或以為 index 又不同步。
- 固定規則：
  - `↑ / ↓` 都要頭尾循環
  - live IME、probe、語言 engine 三邊都要一致

**31. 第一次輸入慢，通常不是「打字慢」，而是暖機太晚**

- 如果第一次切進輸入法或第一次打一個字特別慢，通常是在第一拍才做：
  - lexicon 載入
  - CoreML model 載入
  - 英文詞典初始化
  - mixed merge 熱路徑初始化
- 現在固定原則：
  - prewarm 要在 app 啟動時就做
  - 不要等第一個 session 或第一個 key event 才做
- 至少要暖：
  - 中文 lexicon
  - CoreML ranker
  - 英文 exact/prefix lookup
  - mixed `mergeSpanCoverages` 熱路徑

- 目前正式規則：
  - 一個音節通常至少要有母音／韻母，子音不是必要條件。
  - 例外是可自成音節的聲母，這類單獨也可視為完整音節。
  - 只有 tone、或仍可繼續組成同一音節的前綴，都不算完成。
- 一個音節會在下列情況被視為完成：
  - 已有 `子音(可無) + 母音/韻母`，接著輸入 tone。
  - 已有 `子音(可無) + 母音/韻母`，接著按 `Enter`。
  - 已有 `子音(可無) + 母音/韻母`，接著按 `Space`。
  - 已有 `子音(可無) + 母音/韻母`，接著輸入一個無法再併入當前音節的新符號。
- 這條規則要和小麥注音一致：
  - `currentReading` 只是未完成音節 buffer。
  - tone 一旦進來，該音節就應立即 finalize。
  - `Enter` / `Space` 若遇到非空 `currentReading`，要先 finalize 再 commit / lock。
- 之後若 host、debug、live IME 三邊表現不同，優先檢查是否有哪一條路徑沒遵守這條完成規則。

**29. regression 不能再退回逐句單 process，batch 是正式基線**

- 多 target 一進來後，逐句 CLI 會明顯變慢。
- 已確認最有效的做法是：
  - `build-raw-input-batch`
  - `ime-action-batch-replay`
- 也就是：
  - reverse 用 batch
  - raw replay 也用 batch
- 之後不要再把 regression 改回：
  - 每句一個 `build-raw-input`
  - 每句一個 `ime-action-replay`
- 正確原則：
  - 能 batch 就 batch
  - 單句 replay 只留給 debug，不是正式 baseline
  - 若全量 batch regression 會跑很久，優先直接給 shell 指令，由使用者本機執行後回報

**30. multilingual predict 要直接做 per-target threaded predict**

- 多語架構下，正確模型不是「只切換 current language」。
- 而是：
  - 同一串 raw-key 分別餵給每個 target
  - 各 target 各自 `feed/predict`
  - 最後再做合併排序
- 這條路一旦 target 變多，`predictAll()` 如果串行跑，延遲會快速變差。
- 目前已確立：
  - `predictAll()` 要做 per-target threaded predict
  - 後面的 merge / rank 保持單線程，確保排序穩定
- 之後如果要加第 3、第 4 個語言，不要先優化 UI，先確認：
  - batch regression 還在
  - threaded predict 還在

**31. 正式概念要從 probe 退場，改成整段 raw buffer replay**

- `probe` 是初期開發用的中介概念，不應再當成正式 runtime / CLI / debug 名詞。
- 正式方向是：
  - 維護整串 raw buffer
  - 每次輸入後整段 replay
  - 每個 target 都只對整段 raw buffer 做 `feed/predict`
  - 再做跨 target merge / rank
- 這樣可以避免每個語言自己做邊界判斷，後續加新語言時也不會瘋狂複製切段邏輯。

**32. preview、candidates、commit 不同步

應該要完全由 predict 的結果給這三個

state -> predict -> preview、candidates、commit

- 唯一正式輸出只能是 `presentation`
- `preview` 只能 render `presentation.markedText`
- `candidates` 只能 render `presentation.candidates`
- `commit` 只能送出當下看到的 `presentation.markedText`
- 不允許再保留第二份正文字串給 `commit`
- 不允許 `Enter` / `Space` 先走另一條會改 state 的 commit 支線
- UI helper、cursor lock、debug overlay 都只能影響顯示輔助資訊，不能改寫正式正文

**33. mixed merge 真正慢的通常不是 DP，而是 span coverage 生成**

- 這次把 mixed merge profiling 拆開後，已確認：
  - `mixedMerge.englishSpanScan` 幾乎可以忽略
  - `unified.mergeSpanCoverages.dp` 幾乎可以忽略
  - 真正成本集中在 `unified.mergeSpanCoverages.spanCoverages`
- 所以之後如果 mixed merge 又慢，不要第一時間去怪：
  - 英文 substring 掃描
  - merge DP
- 正確優先順序應該是：
  1. 先看 `spanCoverages`
  2. 再看外層 `session.recomputeRawSpanMerge`
  3. 最後才考慮 DP

**34. preview 已成功的 span，不要再丟回 predict**

- 這次最有效的一刀不是微調 cache，而是把 primary preview 已成功 materialize 的 span 固定下來。
- mixed merge 現在的正確方向是：
  - preview 成功的 primary span 直接當 fixed coverage
  - 只對 preview 沒覆蓋到的 gap 做 `spanCoverages/predict`
- 這樣可以避免：
  - 已成功辨識的中文片段被重算
  - 長 raw buffer 每次都從頭展開 coverage
- 實測結果是：
  - `spanCoverages` 平均延遲從數百毫秒降到數十毫秒級
  - 每字平均耗時也明顯下降

**35. mixed merge 的 cache 命中率不高時，不能指望 cache 救效能**

- 這次 profiling 也看到 `mixedMerge.cacheHit` 很低。
- 代表 raw buffer 在 live 輸入時變化太頻繁，cache 幾乎只是輔助，不是主解法。
- 所以正確策略是：
  - 先讓單次路徑夠快
  - 再把 cache 當額外收益
- 如果單次 `spanCoverages` 還很重，光加 cache 通常不會真的救體感。

**36. DEBUG 頁面要能直接看全局每字耗時**

- 現在偏好設定的 `DEBUG` 分頁除了各熱點平均值，還要顯示：
  - `全局平均耗時：xx.xx ms / 字`
- 這個數值不能用巢狀 profiling 相加，否則一定灌水。
- 正確做法是：
  - 在 `handle(_:, client:)` 的最外層計時
  - 只統計真的有字元內容的 keydown
- 這樣才能把 `readingWalker`、`rankCandidates`、`mixed merge` 之外的外層成本一起算進來。
