## 確認問題

### F01｜P1：提交前未完成延後中英辨識，會送出注音中間狀態

位置：[main.swift:1802](../src/unifyIME/Sources/main.swift#L1802)、[Enter 分支:1149](../src/unifyIME/Sources/main.swift#L1149)。

`scheduleMergeCheck` 把混打辨識延後到停頓之後；提交入口直接讀取 `snapshot()`，再取消尚未執行的合併。Enter 分支只清空待重播工作，沒有呼叫 `flushPendingMerge()`。`deactivateServer` 及系統 `commitComposition` 也會出現相同結果。

重現：逐鍵輸入 `wu0fu4verygood`，在停頓計時器觸發前按 Enter。

- 預期：`天氣 very good`。
- 實際：`天氣ㄒㄍㄐㄗㄕㄟㄟㄎ`。
- 先完成合併或等待計時器再提交，結果正常。
- 三種游標模式、兩組原始輸入、三種提交入口，共 18 個快速情境均失敗。

另確認立即按 Home 會在重建編輯基準時取消尚未完成的辨識；Shift 大寫直輸也可能先送出注音中間狀態。應建立所有提交／重設編輯基準共用的狀態完成步驟，統一處理待重播與待合併工作，避免只補 Enter 單一分支。

證據：`native-initial-results.jsonl`、`native-matrix-results.jsonl`、`native-boundary-results.jsonl`。

### F02｜P1：Caps Lock 字元會直接丟棄尚未送出的組字

位置：[main.swift:1012](../src/unifyIME/Sources/main.swift#L1012)。

Caps Lock 分支在寫入英數字之前呼叫 `clearComposition(client)`。原組字既未提交，也沒有保留下來。

重現：輸入 `su3cl3`，組字顯示「你好」，接著送入帶有 Caps Lock 的 `A`。實際只提交 `a`，原本「你好」消失。三種游標模式均重現；`天氣` 也能重現。

應讓 Caps Lock 直輸沿用統一的組字完成／提交流程，再處理新字元；不要把正常的語言或大小寫切換當成取消組字。

證據：`native-initial-results.jsonl`、`native-matrix-summary.json`。

### F03｜P1：模型安裝失敗後重試，會刪掉正式模型與唯一備份

位置：[install_ranker_model.py:42](../src/unifyIME/scripts/install_ranker_model.py#L42)。

`install_model` 先刪既有 `.bak`，再備份及刪除正式模型，最後才複製來源；來源不存在或複製失敗時沒有還原。

用暫存資料夾內的可用舊模型與不存在的新來源連續呼叫兩次：第一次回報 `FileNotFoundError`，正式模型不存在、備份存在；第二次同樣失敗，正式模型與備份均不存在。CLI 沒有在進入此流程前確保 `.mlmodelc` 來源存在，因此不是只有直接呼叫函式才會遇到的問題。

應先驗證來源並複製至獨立暫存位置，確認可載入後再切換正式路徑；保留上一個成功版本，失敗時還原，且重試不能先刪除唯一恢復來源。

證據：`model-install-retry.json`。測試沒有接觸正式模型。

### F04｜P2：超過 120 個原始按鍵，已辨識英文會退回注音

位置：[main.swift:249](../src/unifyIME/Sources/main.swift#L249)、[RuntimeSupport.swift:122](../src/unifyIME/Sources/App/RuntimeSupport.swift#L122)。

辨識以整段 `rawInputBuffer` 長度作為硬限制。新增按鍵重播後，一旦超過 120，合併直接返回，已辨識的英文也無法恢復。

重現：輸入 `wu0fu4` 重複 19 次，再輸入 `very`，合計 118 鍵；完成辨識後尾端正常顯示 `very`。繼續輸入 `good` 至 122 鍵，即使明確完成待合併工作，尾端仍退成 `ㄒㄍㄐㄗㄕㄟㄟㄎ`，Enter 也提交這串注音。

這是長組字的確定邊界失敗，和 F01 的等待時間不同。應採有界重分析區間並保留前段已解析狀態，或在受控邊界分段完成；不能只停止辨識整段內容。

證據：`native-matrix-results.jsonl` 中的 `length-limit`。

### F05｜P2：新訓練資料的局部座標契約沒有一路傳到模型匯出

位置：[SessionCtl+RankerData.swift:62](../src/unifyIME/Sources/App/SessionCtl+RankerData.swift#L62)、`src/unifyIME/scripts/train_candidate_ranker.py:1800`（本機證據或工具）、[CoreMLCandidateRanker.swift:37](../src/unifyIME/Sources/IME/Ranking/CoreMLCandidateRanker.swift#L37)。

目前未提交的匯出修改使用 `CandidateScoringInput` 的局部 `all_tokens`、局部 `span_start`、最多三個後文音節。Python 訓練直接編碼這些數值，但兩條 Core ML 匯出分支都沒有設定 `unifyime.feature_contract`。執行階段將未標記模型當成 `legacy_segments_v1`，改用全句位置與最多六個後文音節。

實際匯出的長句樣本已確認採局部座標。使用正式 `CandidateScoringInput` 與 `RankingFeatureEncoder` 的座標探針，20 音節、起點 10、跨度 2 時，三個特徵分別變成：

| 特徵索引 | bounded_segments_v2 | legacy_segments_v1 |
| --- | ---: | ---: |
| 6：後文數量 | 3 | 6 |
| 12：起點 | 3 | 10 |
| 14：輸入音節數 | 8 | 20 |

兩者都是 88 維，維度檢查不會擋住此錯配。應由資料集、checkpoint、模型 metadata 共用可驗證的契約版本；舊權重維持其原始格式，不可直接改標籤。此問題影響**用目前新資料重新訓練並經現有 exporter 匯出的模型**，不表示現有發布模型的 legacy 相容方式有錯。訓練腳本為本機忽略檔，仍屬目前工作目錄的訓練流程。

證據：`training-samples.jsonl`、`feature-contract.log`，以及 exporter／loader 靜態比對；未執行完整重新訓練。

### F06｜P2：source-only 備份未包含完整建置所需資源

位置：[backup_common.sh:53](../scripts/backup_common.sh#L53)。

手列備份清單缺少 `Resources/English.tiff`、`Resources/IMEConfig.json`、整個 `Resources/Preferences` 與 `lexicons/README.md`。建置腳本必須複製其中數個檔案，偏好介面也依賴漏掉的 HTML／JS。

依現有清單將建置相關內容還原至全新暫存目錄，執行 `build.sh --skip-sign --no-deploy`，Swift 編譯後確定在複製 `English.tiff` 時退出 1。這次沒有打包或複製與建置無關的私人憑證／歷史資料。

應以完整資源目錄或共用建置清單管理備份內容，並將「從備份還原後可完成建置」納入 smoke，避免新增功能後備份清單再次漏檔。

證據：`backup-coverage.json`、`source-only-restore.log`。

### F07｜P2：MCP 接受的擴充漢字詞彙，被正式多音節組字過濾

位置：[LexiconStore.swift:118](../src/unifyIME/Sources/IME/Lexicon/LexiconStore.swift#L118)、[漢字判定:150](../src/unifyIME/Sources/IME/Lexicon/LexiconStore.swift#L150)、[PersonalVocabularyStore.swift:71](../src/unifyIME/Sources/MCP/PersonalVocabularyStore.swift#L71)。

個人詞庫允許擴充平面漢字，但 `isDisplayableCandidate` 僅接受基本平面的兩個區間；多音節 `compositionCandidates` 因而把這些詞過濾掉。

隔離 MCP 新增 `𠮷野`／`ㄐㄧˊ ㄧㄝˇ`、priority 1000，寫入成功且 `candidate_preview` 首位是 `𠮷野`。另啟動程序讀取同一份資料後，`probe-reading` 精確查詢包含該詞，但組字路徑輸出「及也」，因為該詞根本未進入分詞候選。

應集中漢字範圍與候選資格規則，讓寫入驗證、預覽、字庫與分詞遵循相同契約；避免顯示寫入成功卻無法使用。

證據：`boundary-results.json`。

### F08｜P2：Listwise 模型載入成功狀態與真正排序入口脫節

位置：[CoreMLCandidateRanker.swift:113](../src/unifyIME/Sources/IME/Ranking/CoreMLCandidateRanker.swift#L113)、[CoreMLListwiseCandidateRanker.swift:130](../src/unifyIME/Sources/IME/Ranking/CoreMLListwiseCandidateRanker.swift#L130)。

目前 `listwiseRanker` 僅被建立、查詢 `isModelLoaded` 及輸出狀態；全專案正式來源沒有呼叫它的 `scores(units:context:heuristicScores:)`。外層 `scores` 逐候選使用 scalar 模型，`ranked` 也只走 scalar／heuristic；僅有 Listwise 模型時會在 `model == nil` 的分支直接返回 heuristic。

因此，即使 Listwise 模型載入成功，宣告「可用」也不代表參與排序。[現有說明](../src/unifyIME/LISTWISE_TRANSFORMER.md#L208) 所述的候選視窗與分詞後 Listwise 推論，與目前呼叫路徑不符。

應明確決定此實驗功能是否仍支援：支援時接入共用批次排序入口並驗證確有推論；停用時狀態及文件應反映停用。此項依完整呼叫關係確認，未宣稱測過缺少的 Listwise／ANE 模型。

### F09｜P2：run_cli.sh 無法啟動目前的多檔案 Swift 專案

位置：[run_cli.sh:7](../src/unifyIME/run_cli.sh#L7)。

實測 `zsh src/unifyIME/run_cli.sh ranker-status` 退出 1，出現 `cannot find type 'CandidateSelectionHandler' in scope` 等錯誤。此入口使用 `swift main.swift other.swift...` 腳本形式，沒有將多個來源編譯成目前使用的模組；清單也遺漏英文引擎，且沒有與正式建置維持一致的 framework／入口設定。

應共用 `build_cli.sh` 的來源清單與編譯流程，再執行生成的 CLI；架構及資源定位也應統一，避免保留另一套已失效入口。

證據：`run-cli.log`。

### F10｜P3：CLI 錯誤回應直接插入 row_id，可能輸出非法 JSONL

位置：[IMEProbeSupport.swift:735](../src/unifyIME/Sources/IME/Models/IMEProbeSupport.swift#L735)、[英文入口:967](../src/unifyIME/Sources/IME/Models/IMEProbeSupport.swift#L967)。

正常回應使用 JSON serializer，但重複 ID 等錯誤分支用字串插值建立 JSON。兩筆合法輸入都使用 `row_id = a"b` 時，第一筆正常，第二筆輸出未跳脫引號，接收端無法解析；控制字元也可能破壞一列一物件的格式。退出碼仍正確為 2，因此此項列為較低優先序。

應讓所有成功及失敗回應走同一個 JSON 序列化函式。

證據：`duplicate_quoted_id.jsonl`、`boundary-results.json`。

## 其他觀察與驗證缺口

- `check.sh` 只執行 mixed 與 raw smoke，沒有包含目前 50 個組字追加檢查，也沒有原生事件時序、長輸入界線、MCP、備份還原或模型失敗重試。本次 401/401 與 24/24 均通過，正式流程仍可重現 F01／F02，說明測試覆蓋缺口確實存在。
- `mixed_live_smoke.py` 沒有比對 `has_composition`；`raw_selftest.py` 仍會 trim 並移除 `❚` 後比較。最終文字相同不代表已真正提交，空白差異也可能被忽略。
- `fast_cursor_regression.py` 仍指向舊的 `src/fastChIME/Resources`，且以 Python 字串／查表模擬編輯。它不能作為目前原生游標測試的證據；本次未執行其正式 Application Support 快取寫入流程。
- `build.sh --release` 只省略 `-D DEBUG`，沒有設定 `-O` 等最佳化旗標。這是應釐清的發布建置效能風險；本次未量測最佳化前後延遲，不推估改善倍數。
- 唯一 Swift 編譯警告位於 [PreferencesWindowController.swift:91](../src/unifyIME/Sources/App/PreferencesWindowController.swift#L91)：外層 Task 隱含強捕獲 `self`，內層又使用 `[weak self]`。本次沒有把警告當成已證實的記憶體洩漏。
- 詞庫共 145,887 列 common、236,517 列 phrase、132,092 列英文。phrase 有 1 個重複配對、英文有 2 個重複配對及 9 列欄位不足資料。欄位不足多來自英文解釋中的換行；loader 會忽略，沒有因此重現崩潰。應在產生 TSV 時統一跳脫控制字元並驗證輸出。
